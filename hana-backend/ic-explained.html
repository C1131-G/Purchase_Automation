01 · Big Picture

How Everything Connects

One login = one company. The portal never writes partner SAP directly from the browser — the Node API reacts to save events, a separate worker is the safety-net, and all shared state lives in SBOCOMMON.

🗃️ Portal login store
VST_COMMON (existing) authenticates users to their own company DB. It is reused, never recreated, and new IC tables deliberately have no FK into it — only a soft link via SAP_DB_NAME.
🛠️ IC runtime store
All 13 IC_* tables live in SBOCOMMON (the SAP common DB) so one engine sees every company's config, RFQs, mappings, notifications and retry queue over a single connection.
🔗 Partner documents
Real SAP documents (SQ, AR Invoice) are created inside each company's own tenant DB through the SAP Service Layer, logged in per company via IC_SAP_CONNECTION.

Architecture FAQ

Why is IC data in SBOCOMMON instead of each company DB?
RFQs, document mappings, notifications and retry rows are cross-company. One shared schema lets the worker and API see every participant without opening six tenant databases for metadata. Real SAP documents (PQ, SQ, AR) still live in each company's own tenant DB via Service Layer.
Can an IC failure block the user's PQ or PO save?
No. Hooks afterPqSaved and afterPoCreated return immediately and run flows in the background. A Service Layer timeout on the partner side enqueues IC_RETRY_QUEUE instead of rolling back the buyer document.
How does the portal know which company I am?
Session dbName maps to IC_COMPANY.SAP_DB_NAME. Every IC API scopes RFQs, notifications and retries to that company ID. Seller actions require TARGET_COMPANY_ID; buyer actions require SOURCE_COMPANY_ID.

Database FAQ

What is IC_DOCUMENT_MAPPING used for?
It is the source of truth for cross-company document links: PQ_DRAFT→RFQ, RFQ→PQ, RFQ→SQ, PO→AR_DRAFT. The relationship map API and frontend hover UI read these rows. Each mapping stores source/target company, object code, doc entry/num, status and optional error text.
Why is RFQ data not in SAP ODRF/OQUT?
RFQ is a custom IC workflow (seller fills prices before buyer converts). It lives in IC_RFQ_HEADER / IC_RFQ_LINE until convert creates real SAP PQ + SQ. RFQ numbers display as plain doc nums (e.g. 8000590), not RFQ-PQD-* prefixes.
What happens when convert fails mid-way?
Mapping rows may stay PENDING or ERROR; a FLOW1_CONVERT_PQ_SQ retry row is inserted. The worker replays convert idempotently (checks existing mappings before re-creating SQ).

04 · Flow 1 — Company to Company

PQ Draft → RFQ → Convert → Real PQ + SQ

A buyer in Company A saves a Purchase Quotation draft whose vendor is an intercompany vendor. The engine opens a custom RFQ for Company B (the seller), the seller fills prices, and the buyer converts — producing a real PQ in A and a real Sales Quotation in B. Gated by ENABLE_FLOW1_RFQ_CHAIN.

Flow 1 FAQ

Who can submit vs convert?
Seller (Company B) fills prices and submits RFQ (SUBMITTED). Buyer (Company A) runs convert, which posts PQ in A and auto-creates SQ in B. Role checks use session company vs RFQ source/target IDs.
How is RFQ linked to the auto-generated SQ?
On successful convert, IC_DOCUMENT_MAPPING writes RFQ→SQ with source = buyer company + RFQ id, target = seller company + SQ DocEntry. The relationship map reads this row — not SAP base-document fields.
What tax goes on the seller SQ?
Buyer PQ line tax (e.g. IN-12.5, OVTG Category I) is looked up on Company A. The engine finds a matching Rate on Company B OVTG with Category O (e.g. OUT-12.5). Falls back to item/BP tax if no OVTG match. See Tax section.
Can the same PQ create two RFQs?
No — idempotent capture checks IC_DOCUMENT_MAPPING for an existing PQ_DRAFT→RFQ row before creating a new header. Retry replays the same RFQ id.

Flow 2 FAQ

Does Flow 2 need a prior RFQ?
No. Flow 2 is independent: any posted PO with an IC vendor triggers AR Invoice creation on the seller. Flow 1 and Flow 2 can both be enabled.
How is PO line tax mapped to AR Invoice?
Same OVTG rate engine as PQ→SQ: read buyer PO VatGroup on Company A OVTG (Category I), find seller OVTG with same Rate and Category O. Logged per line in ic-tax-usage as poTaxCode + arTaxCode.
What SAP object is created in Company B?
An AR Invoice (ObjType 13 / ODRF), not a posted AR invoice. Finance posts it manually in SAP B1 when ready. Mapping object code is AR_DRAFT.

Remarks FAQ

Why did we change from IC | KEY format?
Business users read SAP Comments directly. Based on Purchase Order 5001328 is clearer than IC | PO: …. Legacy lines remain parseable so re-running convert does not duplicate links.
Will convert duplicate remark lines?
No — parseIcRemarkKeys() collects existing keys before append. Each of PQD, RFQ, PQ, SQ, PO, AR can appear at most once in the chain.
What RFQ number appears in remarks?
Plain PQ doc num (e.g. 8000590), not RFQ-PQD-*. Matches RFQ table display via formatRfqDocNumber / parseRfqDisplayNum.

Relationship Map FAQ

Why only RFQ and SQ for IC sales quotations?
IC Flow 1 ends at seller SQ. Downstream SO/AR on the seller DB are normal SAP docs, not IC-driven. Showing them would confuse users; the map reflects the IC contract only.
RFQ hover shows no SQ — why?
SQ appears only after buyer convert succeeds and IC_DOCUMENT_MAPPING has RFQ→SQ with status SUCCESS. Before convert, RFQ node is active and SQ is inactive.
Where is the mapping stored?
IC_DOCUMENT_MAPPING: SOURCE_OBJECT=RFQ, TARGET_OBJECT=SQ, TARGET_DOC_ENTRY = seller SQ DocEntry. Not stored in SAP UDFs.
06 · Notifications & Retry Engine

What Happens When Something Fails

Every cross-company action is wrapped: success → map + notify; failure → freeze the action into IC_RETRY_QUEUE and let the worker replay it. Users watch progress on the Intercompany Activity page.

🔔 Company-scoped inbox
Notifications are written with the recipient COMPANY_ID — Company B never sees A's alerts. APIs: GET /notifications, GET /notifications/unread-count (header badge), PATCH /:id/read, POST /mark-all-read.
🛡️ What raises one
New RFQ for seller, RFQ submitted for buyer, SQ created, AR Invoice created, and every retry attempt/exhaustion — each with PRIORITY (HIGH/MEDIUM) and a FLOW_STEP like FLOW1_RFQ_CREATED.
📊 Fully auditable
Every attempt (auto or manual) also lands in IC_SYNC_HISTORY and SL traffic in IC_API_LOG with masked secrets — ops can reconstruct any incident.

Retry lifecycle (state machine)

WAITING→ worker claims due row → PROCESSING→ handler OK → SUCCESS
PROCESSING→ handler throws → RETRY_COUNT + 1 → back to WAITING(NEXT_RETRY_AT = now + RETRY_DELAY_MINUTES) … or when count ≥ MAX_RETRY_COUNT (2) → DEAD
Action code (ACTION_CODE) Replays Enqueued by
FLOW1_CREATE_RFQ Rebuild the custom RFQ from a captured PQ Flow 1 steps 01–02
FLOW1_CONVERT_PQ_SQ Re-apply prices, convert draft → PQ, create seller SQ Flow 1 step 05
FLOW1_SUBMIT_RFQ Re-submit a seller-filled RFQ Flow 1 step 04
FLOW2_CREATE_AR_DRAFT Re-post the AR Invoice to the partner SL Flow 2 steps 02–03
FLOW2_MAP_NOTIFY Re-run the mapping + notification after a late success Flow 2 step 04

The worker — 3 jobs every loop

Job (IC_SCHEDULER_JOB.JOB_NAME) What it does Cadence
DETECT_PQ_DRAFT Safety net: for each active IC_COMPANY, logs into its SL and finds new PQ drafts with IC vendors; creates the RFQ if none exists (covers API downtime). Hybrid design: hook is primary, worker is the net. DETECT_DRAFT_CRON_MINUTES
PROCESS_RETRY Claims due WAITING rows (NEXT_RETRY_AT ≤ now, count < max), replays the handler for each ACTION_CODE, marks SUCCESS / re-WAITING / DEAD, and notifies on exhaustion. every loop

Retry FAQ

How many times will the worker retry?
Default MAX_RETRY_COUNT = 2 from IC_CONFIGURATION. After that the row becomes DEAD and a notification is raised. Ops can still force POST /retries/:id/run.
Convert failed but PQ was created — is it safe to retry?
Yes — FLOW1_CONVERT_PQ_SQ handler checks existing mappings and RFQ status. It will not create duplicate SQs if mapping already succeeded.
Do I need the worker if hooks work?
Yes for production. Hooks are primary; worker DETECT_PQ_DRAFT is the safety net when API was down during save, and PROCESS_RETRY replays failures.
07 · Tax Code Selection (OVTG)

Cross-Company Tax via OVTG Rate + Category

There is no IC_TAX_MAPPING table. Tax is resolved by config/tax-mapping/resolve-partner-tax.service.ts using SAP OVTG: purchase lines use Category I (Input), sales lines use Category O (Output). The Rate must match across companies.

0️⃣
OVTG rate match
source = "ovtg_rate"
Read buyer tax on Company A OVTG → same Rate on Company B OVTG with opposite category (I→O for PQ→SQ and PO→AR).
1️⃣
Item master tax
source = "item"
OITM.VatGourpSa on the seller's own DB (sales side).
2️⃣
BP default tax
source = "bp"
OCRD.ECVatGroup of the IC customer on the seller's DB.
3️⃣
Omit VatGroup
source = "omit"
No VatGroup sent → SAP tax determination on POST. Logged with seeding hint. 
# Example: PQ line IN-12.5 on Company A (buyer)
SELECT "Code","Category","Rate" FROM "OVTG" WHERE "Code" = 'IN-12.5'
  → Category I, Rate 12.5

# Find seller sales tax on Company B with same rate:
SELECT "Code" FROM "OVTG" WHERE "Category" = 'O' AND "Rate" = 12.5
  → e.g. OUT-12.5 used on SQ / AR Invoice line

# Pure logic: map-ovtg-partner-tax.ts · HANA: partner-tax.masters.ts
⚠️Golden rule: buyer purchase codes like IN-12.5 are never copied verbatim onto seller sales lines. They are used only to lookup the rate on buyer OVTG, then pick the matching seller output tax. RFQ/PQ lines still store buyer tax snapshot for re-applying to buyer PQ at convert.

Tax ownership by document

Document Company Tax family How obtained
PQ Draft Buyer Purchase UI / SAP buyer defaults
RFQ line — Snapshot only Buyer draft VatGroup — re-applied to the PQ only, never seller tax
PQ (after convert) Buyer Purchase RFQ snapshot = buyer tax
SQ (seller) Seller Sales OVTG rate match (I→O) → item VatGourpSa → BP ECVatGroup → omit
PO Buyer Purchase Normal buyer PO posting
AR Invoice Seller Sales Same OVTG + fallback chain as SQ
AR final (manual) Seller Sales User posts in SAP B1 from the draft
🔧Ops checklist: for each company pair, ensure OVTG has matching Rate rows for Category I (buyer) and O (seller). Also set seller item sales tax (OITM.VatGourpSa) and IC customer BP tax (OCRD.ECVatGroup) as fallbacks. Per-line audit: ic-tax-usage.ts on convert/AR build logs pqTaxCode / sqTaxCode or poTaxCode / arTaxCode.

Tax FAQ

IN-12.5 on buyer — what should seller SQ use?
Look up IN-12.5 on buyer OVTG (Rate 12.5, Category I). On seller OVTG, pick the sales code with Rate 12.5 and Category O (e.g. OUT-12.5). Code names can differ; rate + category are what match.
What if seller has no matching O rate?
Resolver falls back to item master, then BP default, then omit. Check IC logs (IC_LOG_SCOPE.TAX) for source: "omit" and fix OVTG or OITM/OCRD on the seller company.
Does reverse mapping (sales → purchase) work?
Yes — map-ovtg-partner-tax.ts picks target category from docSide. For purchase targets, it finds Category I at the same rate as the source sales tax.
08 · Warehouse & Branch Selection

How the Seller Warehouse & Branch Are Chosen

Multi-branch SAP companies require the document branch and every line warehouse to agree. Implemented in config/warehouse/partner-warehouse.masters.ts + flows/flow-1.../create-seller-sq.ts.

🏫
Branch first
IC_COMPANY
DEFAULT_BRANCH_ID of the seller company → set as BPL_IDAssignedToInvoice on the SQ / AR Invoice header.
📦
Line WH: item default
preferred
Item's OITM.DfltWH — but only if that warehouse is active and assigned to the same branch (OWHS.BPLid).
🏚
Line WH: branch fallback
fallback
First active warehouse on the document branch (OWHS where Inactive='N' and BPLid = branch, ordered by WhsCode).
⏻
Omit otherwise
safe
No branch configured or no match → WarehouseCode omitted and SAP applies its own default. 
-- branch default WH (document-level fallback for all lines)
SELECT TOP 1 "WhsCode" FROM "OWHS"
 WHERE "Inactive" = 'N' AND "BPLid" = ?  ORDER BY "WhsCode" ASC

-- per-line WH: item default WH only when it lives on the same branch
SELECT TOP 1 T0."DfltWH" AS "WhsCode"
   FROM "OITM" T0 INNER JOIN "OWHS" T1 ON T1."WhsCode" = T0."DfltWH"
  WHERE T0."ItemCode" = ? AND T1."Inactive" = 'N' AND T1."BPLid" = ?

-- final line rule
WarehouseCode = itemWhOnBranch ?? branchWarehouse ?? (omit)
🚫Never copy the buyer warehouse. A buyer WH like L101 may belong to a different branch (BPL 7) than the seller document (BPL 1) — SAP would reject or mis-assign it. The engine always resolves the seller's own warehouse on the document's branch. Same principle as tax: company-local, never cross-copied.

Warehouse FAQ

Why did SQ fail with "No active warehouse on branch"?
Seller IC_COMPANY.DEFAULT_BRANCH_ID is set but no active OWHS row exists with matching BPLid. Add a warehouse on that branch or fix the default branch id.
Can we use the buyer's warehouse code on SQ?
No — buyer WH may belong to a different branch on the seller DB and SAP will reject or mis-post. Always resolve seller WH on the document branch.
